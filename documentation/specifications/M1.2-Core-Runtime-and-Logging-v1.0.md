# AETHER ENGINE M1.2 Engineering Specification v1.0
## Core Runtime and Logging

**Status:** Owner-approved implementation baseline  
**Milestone:** M1.2 — Core Runtime and Logging  
**Depends on:** M1.1 — Native Platform Foundation (merged)  
**Implementation status:** Partially implemented. The status/logging foundation is merged; module orchestration, application lifecycle, clock and event dispatcher remain pending. This document defines the approved implementation contract for the remaining M1.2 work.

---

## 1. Purpose

M1.2 establishes the engine's deterministic application lifecycle, module orchestration, diagnostics/logging, monotonic frame-time measurement and a small engine-owned event foundation. It must remain independent of SDL3 and must not introduce renderer, physics, ECS, scripting, networking or editor dependencies.

The deliverable is a reusable native runtime library with focused automated tests. It is not yet a complete game loop executable or a playable engine.

## 2. Scope

### Included

1. Core status/error reporting for lifecycle operations.
2. Engine-owned logging API and console sink.
3. Module registration, dependency validation and deterministic startup/update/shutdown order.
4. Application lifecycle state machine with safe rollback after partial initialization.
5. Monotonic clock and frame-time value.
6. Typed synchronous event dispatch foundation.
7. Unit and integration tests, CI integration and developer documentation.

### Explicitly excluded

- Window creation and SDL event polling (owned by M1.1 platform).
- Renderer, GPU resources, Vulkan surfaces or graphics loop.
- ECS, scenes, memory allocators and job scheduler (later milestones).
- Gameplay scripting, AI, physics, audio and networking.
- File logging, log rotation, remote logging and telemetry.
- Asynchronous event dispatch and cross-thread event delivery.
- A production game executable or editor.

## 3. Architectural constraints

- C++20; CMake 3.25+.
- Preserve the AETHER-owned public API boundary; SDL3 types must not appear in core headers.
- Core runtime must work without a window, GPU, network connection or external service.
- Keep third-party dependencies out of M1.2 unless separately approved.
- Keep tests deterministic and runnable in GitHub Actions on Linux and Windows.
- Existing M1.1 platform target and tests must remain green.
- Public headers live under `engine/aether/core/`; implementation files live under `engine/core/src/`.
- Core target is a static library exposed as `Aether::Core`.

## 4. Public API contract

The following names and signatures are proposed as the M1.2 public contract. Implementation may refine private details, but changes to public behavior require review.

### 4.1 Status and errors

```cpp
namespace aether::core {

enum class ErrorCode : std::uint8_t {
    None,
    InvalidState,
    InvalidArgument,
    DuplicateModule,
    MissingDependency,
    DependencyCycle,
    ModuleInitializationFailed,
    ModuleUpdateFailed,
    ModuleShutdownFailed,
    InternalError
};

struct Status final {
    ErrorCode code{ErrorCode::None};
    std::string message;

    [[nodiscard]] bool ok() const noexcept;
    explicit operator bool() const noexcept;
    static Status success();
    static Status failure(ErrorCode code, std::string message);
};

} // namespace aether::core
```

Success is represented by `ErrorCode::None`. A failed status must carry a useful diagnostic message. APIs that can fail return `Status`; destructors remain non-throwing and cannot be used as the primary error-reporting channel.

### 4.2 Logging

```cpp
enum class LogLevel : std::uint8_t { Trace, Debug, Info, Warning, Error, Critical, Off };

class ILogSink {
public:
    virtual ~ILogSink() = default;
    virtual void write(LogLevel level,
                       std::string_view category,
                       std::string_view message) = 0;
};

class ConsoleLogSink final : public ILogSink {
public:
    void write(LogLevel level,
               std::string_view category,
               std::string_view message) override;
};

class Logger final {
public:
    // Throws std::invalid_argument when sink is null.
    explicit Logger(std::shared_ptr<ILogSink> sink);
    void set_level(LogLevel level) noexcept;
    [[nodiscard]] LogLevel level() const noexcept;
    void log(LogLevel level,
             std::string_view category,
             std::string_view message);
};

```

- Logger owns a shared sink reference; construction with a null sink throws `std::invalid_argument`.
- `set_level()`, `level()` and `log()` may be called concurrently on the same Logger. The configured threshold must be read and written under synchronization; a call to `log()` observes one complete threshold value for its filtering decision. Callers do not need to externally serialize threshold changes with logging.
- Each Logger serializes calls it makes to its sink. Because multiple Logger instances may share one sink, every `ILogSink` implementation must also be safe for concurrent calls originating from different Logger instances. Sink implementations with mutable state must provide their own synchronization; `ConsoleLogSink` serializes its own writes. Per-logger serialization alone does not make a shared sink thread-safe.
- Messages below the configured threshold and all messages when level is `Off` are discarded.
- Console output goes to standard error. Each record includes a wall-clock timestamp, level and category.
- M1.2 does not promise stable machine-readable JSON output.
- Logging must not call back into the application lifecycle.

### 4.3 Module contract

```cpp
using ModuleId = std::string;

struct RuntimeContext final {
    Logger& logger;
};

struct FrameContext final {
    double delta_seconds{0.0};
    double elapsed_seconds{0.0};
    std::uint64_t frame_index{0};
};

class IModule {
public:
    virtual ~IModule() = default;
    [[nodiscard]] virtual std::string_view name() const noexcept = 0;
    [[nodiscard]] virtual std::span<const ModuleId> dependencies() const noexcept = 0;
    virtual Status on_initialize(RuntimeContext& context) = 0;
    virtual Status on_update(const FrameContext& frame) = 0;
    virtual Status on_shutdown() = 0;
};
```

- Modules are owned by the registry through `std::unique_ptr<IModule>`.
- Module names are unique, non-empty identifiers; duplicate registration fails.
- Dependencies name other registered modules. Missing dependencies and cycles fail validation before any module is initialized.
- Startup order is a deterministic topological ordering; among otherwise-ready modules, registration order is preserved.
- Update order matches startup order.
- Shutdown order is the reverse of the successfully initialized order.
- A module is considered initialized only after `on_initialize` returns success.
- Every module callback (`on_initialize`, `on_update`, and `on_shutdown`) is invoked through an exception boundary. A thrown `std::exception` becomes a failed `Status` containing the callback name and `what()` text. Any non-standard exception becomes a failed `Status` identifying the callback and an unknown exception. Exceptions must never escape the application lifecycle orchestration API.
- If `on_initialize` returns failure or throws, the registry invokes `on_shutdown` on that same failing module exactly once as best-effort cleanup of partially acquired resources. `on_shutdown` must therefore be safe after partial initialization and must tolerate repeated internal cleanup attempts without undefined behavior. The failing module is not added to the successfully initialized list. Previously initialized modules are then shut down in reverse order.
- If cleanup of the failing module or rollback of earlier modules fails, those cleanup failures are appended to the original initialization failure; the original initialization failure remains primary.
- Shutdown attempts every module in the cleanup list even if one `on_shutdown` returns failure or throws. Each thrown shutdown exception is converted to a failed `Status`; the first shutdown failure is returned and later failures are appended to its diagnostic message.
- If update returns failure or throws, the application transitions to `Failed` and shuts down all successfully initialized modules in reverse order. The update failure remains the primary status; shutdown failures are appended.
- Any failure during explicit shutdown causes the application to enter `Failed` and store the aggregated shutdown failure. A subsequent `shutdown()` returns that stored failure without invoking module shutdown callbacks again. If every cleanup callback succeeds, the application enters `Stopped`; subsequent shutdown calls return success without repeating callbacks.

### 4.4 Application lifecycle

```cpp
enum class ApplicationState : std::uint8_t {
    Created, Initializing, Running, Stopping, Stopped, Failed
};

class ModuleRegistry final {
public:
    [[nodiscard]] Status add(std::unique_ptr<IModule> module);
    [[nodiscard]] Status validate();

private:
    friend class Application;
    // Owns modules and caches the deterministic dependency order after validation.
};

class Application final {
public:
    Application(Logger& logger, ModuleRegistry modules);
    [[nodiscard]] Status initialize();
    [[nodiscard]] Status update(const FrameContext& frame);
    [[nodiscard]] Status shutdown();
    [[nodiscard]] ApplicationState state() const noexcept;
};
```

- Legal normal path: Created → Initializing → Running → Stopping → Stopped.
- Initialization failure transitions to Failed after rollback.
- Update failure transitions to Failed after rollback.
- Calling `update` before successful initialization or after stopping/stopped/failed returns InvalidState and does not invoke modules.
- Calling `initialize` more than once returns InvalidState.
- Calling `shutdown` in Created transitions directly to Stopped successfully.
- Calling `shutdown` in Stopped succeeds idempotently.
- Calling `shutdown` in Failed does not repeat module shutdown; it returns the stored failure.
- `Application` does not own the logger. The module registry is moved into the application and owns registered modules.
- No implicit background thread or platform event pump is started.

### 4.5 Clock

```cpp
class Clock final {
public:
    void reset() noexcept;
    [[nodiscard]] FrameContext tick() noexcept;
};
```

- Uses `std::chrono::steady_clock`; wall-clock changes must not make frame delta negative.
- First tick after reset returns zero delta and zero elapsed time.
- Later ticks return non-negative delta and elapsed seconds since reset.
- Frame index starts at zero and increments once per tick after the initial baseline tick.
- Clock does not sleep, throttle or clamp frame time in M1.2.

### 4.6 Typed synchronous event dispatcher

```cpp
struct Subscription final {
    std::uint64_t value{0};
    friend bool operator==(Subscription, Subscription) = default;
};

class EventDispatcher final {
public:
    template<class Event>
    using Handler = std::function<void(const Event&)>;

    template<class Event>
    Subscription subscribe(Handler<Event> handler);

    template<class Event>
    [[nodiscard]] Status dispatch(const Event& event);
    void unsubscribe(Subscription subscription) noexcept;
};
```

- Event types are ordinary C++ value types; the dispatcher does not require inheritance from a common event base.
- Dispatch is synchronous on the calling thread.
- Handlers for one event type run in subscription order.
- Dispatch uses a stable snapshot: subscriptions added during dispatch do not receive the in-progress event; subscriptions removed during dispatch are skipped if they have not yet run.
- A handler exception is caught; remaining handlers still run. Dispatch returns success when every handler completes, otherwise an InternalError status whose message identifies the number of handlers that failed.
- Dispatcher is single-thread confined in M1.2; concurrent subscribe, unsubscribe or dispatch is unsupported and documented.

## 5. Lifecycle and failure behavior

| Situation | Required result |
|---|---|
| Duplicate module name | Registration fails; registry remains unchanged |
| Missing dependency | Initialization fails before any module callback |
| Dependency cycle | Initialization fails before any module callback |
| Module initialization failure | Invoke `on_shutdown` once on the failing module for partial cleanup, then roll back prior successful modules in reverse order; preserve the initialization failure as primary |
| Module update failure or exception | Convert exception to Status if needed; transition to Failed and roll back initialized modules in reverse order |
| One module shutdown fails or throws | Continue shutting down all remaining modules; enter Failed and store aggregated failure; later shutdown calls return it without repeating callbacks |
| Update while not Running | Return InvalidState; no module update callbacks |
| Repeated shutdown after Stopped | Return success without repeating callbacks |
| Logger level Off | No sink writes |
| Clock reset then first tick | Zero delta and zero elapsed |
| Event handler throws | Continue dispatching remaining handlers and report failure |
| Module callback throws | Convert exception to failed Status; perform the same cleanup as a returned failure |
| Failing module initialization | Call its `on_shutdown` once for partial-resource cleanup before rolling back prior modules |

## 7. Build and test requirements

- Add `engine/core` as a CMake subdirectory and expose `Aether::Core`.
- Link tests only to `Aether::Core`; tests must not require SDL initialization.
- Register focused CTest targets or one executable with named test cases.
- CI runs core and existing platform tests on Linux and Windows.
- No test requires a GPU, display server, internet connection after configure, or external service.
- All tests must pass in Debug and Release configurations.

Required test cases:
1. Status success/failure values preserve code and message.
2. Logger construction rejects a null sink with `std::invalid_argument`.
2. Logger threshold filters lower levels; Off filters all; sink receives category and message; concurrent writes produce complete non-interleaved records.
3. Registry rejects duplicate names, missing dependencies and cycles before callbacks.
4. Dependency ordering is deterministic and respects registration order for independent modules.
5. Initialization failure rolls back only earlier successful modules in reverse order.
6. Update receives the exact frame context and runs in startup order.
7. Update failure triggers reverse-order shutdown and preserves the primary failure.
8. Shutdown attempts every module and aggregates failures.
9. Application rejects illegal lifecycle transitions and repeated initialization.
10. Clock first tick, monotonic delta, elapsed time and frame index.
11. Event subscription order, unsubscribe, subscription changes during dispatch, and handler exception continuation/reporting.

## 8. Implementation tasks

### Task 1 — Status and logging foundation
Implement `Status`, `ErrorCode`, `LogLevel`, `ILogSink`, `ConsoleLogSink` and `Logger`. Add focused tests for status semantics, level filtering, formatting and concurrent record integrity.

### Task 2 — Module registry and dependency ordering
Implement module ownership, unique-name registration, dependency validation and deterministic topological ordering. Test duplicate names, missing dependencies, cycles, stable ordering and empty registry.

### Task 3 — Application lifecycle and rollback
Implement the state machine and callback orchestration. Test every legal and illegal transition, partial initialization rollback, update failure, reverse shutdown and aggregated shutdown errors.

### Task 4 — Clock, event dispatcher and integration
Implement the monotonic clock and synchronous typed event dispatcher. Integrate core tests into CMake and CI, preserve platform tests, and document threading/lifecycle contracts.

Each task must be independently testable and committed only after its focused tests pass. A draft PR should be opened for M1.2 implementation after the specification is approved.

## 9. Acceptance criteria

M1.2 is eligible for acceptance only when:

- `Aether::Core` builds on Windows and Linux with C++20.
- All required test cases pass in Debug and Release CI.
- Module dependency ordering is deterministic and validated before callbacks.
- Every partial initialization and update failure produces safe reverse-order cleanup.
- Shutdown failures do not prevent cleanup of remaining initialized modules.
- Application lifecycle transitions are enforced.
- Clock uses a monotonic source and has deterministic reset/first-tick behavior.
- Event dispatch semantics and threading restrictions are documented and tested.
- Logging is thread-safe at the record boundary and has no mandatory third-party dependency.
- M1.1 platform tests remain green.
- Documentation accurately distinguishes implemented runtime functionality from future engine systems.

## 10. Approved owner decisions

1. **Module update failure policy:** Fail fast on the first module update failure, transition the application to Failed, and shut down initialized modules in reverse order. Preserve the update failure as primary and append cleanup failures.
2. **Log timestamp format:** Emit UTC ISO-8601 timestamps with millisecond precision to standard error.
3. **Shared sink concurrency:** Each `ILogSink` implementation is responsible for being safe when multiple Logger instances call it concurrently. Per-logger serialization remains guaranteed by `Logger`; sinks with mutable state must synchronize internally.
4. **Module callback exceptions:** Convert standard and non-standard exceptions from all module callbacks into failed `Status` values and apply the same rollback/continued-shutdown behavior as returned failures.
5. **Partial initialization cleanup:** If `on_initialize` fails or throws, invoke that module's `on_shutdown` once for best-effort cleanup before rolling back previously initialized modules. The module contract requires `on_shutdown` to tolerate partial initialization.
6. **Failed shutdown state:** If any cleanup callback fails, the application enters `Failed`, stores the aggregate failure, and subsequent `shutdown()` calls return that stored failure without repeating callbacks.

The specification is the approved contract for remaining M1.2 implementation. Any change to these public behaviors requires owner review before implementation.
